# ArkTS 三方库适配流程合成测试样例

欢迎加入CPF-ApplicationTPC 原生库社区：【https://atomgit.com/CPF-ApplicationTPC】

> 本文仅作为 CPF-Skills 仓库的端到端测试夹具，不代表任何真实三方库适配经历，也不能作为征文、提交或真机验证证据。

## 测试目的

这个样例用于验证项目中的资格结果、验证门禁、文章素材包、静态文章检查和完整合规报告能够按照固定契约串联执行。样例名称 ExampleLibrary 是占位名称，所有提交、日志、构建、测试、设备和截图引用都使用 fixture 协议，表示它们只存在于测试数据中。测试代码必须把这些引用视为结构化输入，而不是现实世界中已经发生的开发事实。这样可以在持续集成环境中验证状态机、字段约束和路由逻辑，同时避免把自动测试数据包装成真实实践材料。

## 资格与验证夹具

资格夹具把候选状态设置为 RECOMMENDED，只用于证明文章素材包要求的前置状态能够被正确读取。它不表示 ExampleLibrary 在现实活动中已经完成去重，也不表示该名称对应真实包。验证夹具包含实现、构建、演示、测试、实体设备运行和截图六类检查，并把它们设置为 VERIFIED；每一类检查都附带 fixture 引用。设备字段使用 physical 与 HarmonyOS，是为了覆盖 Validation Gate 的结构校验分支，而不是声明测试人员真的拿某一台设备运行过示例。真实项目必须把这些占位引用替换为可审计的提交、构建日志、测试报告、设备记录和截图文件。

## 素材包组合

素材包测试会读取资格结果、Validation Gate 输出和开发记录。开发记录同样是合成数据，只用于确认 problems、decisions、api_changes 与 source_refs 能被映射到文章章节。如果这些字段为空，脚本应该产生 material_gaps，而不是由模型补写一个看似完整的问题解决故事。这个约束对真实征文尤其重要，因为文章中的故障、失败尝试和技术取舍必须来自作者实际开发过程。测试通过只说明程序能正确区分“已有材料”和“材料缺口”，不能说明真实适配已经发生。

## 静态文章检查

本文件同时用于验证 Markdown H1、框架名称、非代码中文字符数量、社区引导语和图片引用等静态规则。这里刻意写出足够长度的中文说明，是为了触发字数规则的通过分支。静态检查不会判断原创性、重复率、人工写作比例或真机截图真实性，这些规则必须继续由外部指标、作者确认和 Validation Gate 提供。即使本测试得到 static_status 为 PASS，也只能解释为静态格式与可确定性内容规则通过，不能把它升级成现实活动资格。

## 完整合规报告

合规上下文为重复率、质量分和人工确认项提供固定测试值，使完整报告能够覆盖 READY_TO_PUBLISH 分支。这里的 READY_TO_PUBLISH 只属于 fixture 的闭环测试结果，表示在这组人工构造输入中没有未完成的发布前规则。真实文章只有在实际外部检查结果、真实作者确认和真实 Validation Gate 全部提供后，才能得到同样状态。阅读量仍被保留为发布后指标，因此它不会因为测试值较低而阻塞发布前状态。

## 使用边界

维护者可以修改脚本、规则或 Skill 后运行这个端到端夹具，确认不同层之间没有字段漂移。如果未来 schema 发生破坏性变化，测试应首先失败，然后由维护者显式更新 fixture 和断言。任何工具都不得把 fixture 协议解释成实际证据，也不得把这个 Markdown 文件发布为活动征文。真实样例应建立独立目录，并保存能够追溯到真实仓库、真实构建、真实测试、真实设备和真实截图的引用，再由相同脚本链处理。

## 结论

这个合成样例的价值是验证“程序是否按规则工作”，而不是证明“某个库已经适配完成”。只有把测试数据和现实证据严格分开，项目才能同时获得稳定回归测试与可信活动流程。后续接入真实适配项目时，应保持同一数据契约，但必须替换全部 fixture 引用，并重新执行资格、验证、文章检查和外部指标流程。
